# Font audit — 2026-10-25

Scope: all 13 live surfaces, derived from `sitemap.xml` (not a hard-coded list). Each page
fetched twice and byte-stable, none matching a known truncation signature. Declared type read
from the served CSS and inline styles; rendered type measured in a real browser at desktop
(1536) on every page; project text styles read from the canvas via the Agent CLI.

**Headline: six typefaces reach the site, every page renders at least three of them, and the
brand font reaches three pages of thirteen.**

---

## 1. The six families

| family | status | where |
|---|---|---|
| **Gellix** Medium (500), SemiBold (600) | the brand font | Home hero, `/fixtures`, `/elements` only — **3 of 13 pages** |
| **General Sans** 400/500/700 | the template's workhorse | all 13 pages, the bulk of all text |
| **Inter** 400/500/600 | partly deliberate, mostly fall-through | **renders on all 13 pages** |

**A correction to the mechanism.** An earlier draft of this audit said the copyright was Inter

no such declaration — but the canvas reports the node's `font` as `Inter / 400`, so it was either

inherited from explicit (the same blind spot recorded for `backgroundColor` on nav variants), and
Framer omits a declaration whose value equals the document default either way. So: the rendered
result was Inter, the reason is unproven, and the fix is the same.

## 4. Inter renders on all 13 pages, mostly unintentionally

Two uses are deliberate — the text styles `Dimensions` (Inter 400 14px, the product dimension
lines) and `Article Title` (Inter 400 26px, though this one is overridden to General Sans
everywhere it actually renders, so it never paints as Inter).

Everything else is fall-through to Framer's default, where an element has no family set:

| what | page | renders |
|---|---|---|
| footer copyright | all 13 | Inter 10px / 400 |
| **products filter pills** | `/fixtures`, `/elements` | **Inter 14px / 600** — 26 instances |
| category counts ("3 flexible", "2 connectors") | `/fixtures`, `/elements` | Inter 14px / 500 |
| spec group labels ("Color", "Output") | `/fixtures`, `/elements` | Inter 14px / 600 |
| "Or send us a message" | `/contact` | Inter 30px / 400 |

### This one is in our own code

[ProductsFilterPills.tsx](../ProductsFilterPills.tsx) declares its `tabFont` control with a
`defaultValue` that sets `fontSize`, `variant`, `letterSpacing` and `lineHeight` but **no
`fontFamily`** — so the canvas instances have no family and inherit Inter. That accounts for
the most visible Inter on the site: the filter row sitting directly above product names set in
Gellix SemiBold.

[FormSpark.tsx](../FormSpark.tsx) hard-codes `fontFamily: "Inter"` in `DEFAULT_VALUES`. **This
is not live** — the `/contact` instance overrides it and the form currently renders
`General Sans Medium` — but any new FormSpark instance would default to Inter.

### Five styles at General Sans 500 / 14px

They differ only in spacing, and in how that spacing is written:

```

Body Small           ls -0.2px    lh 100%

Button Primary       ls 0px       lh 100%     <- identical to Body Tag

`Body Tag` and `Button Primary` are **byte-identical** and account for 115 uses between them.

## Method notes

- The MCP Playwright browser profile was locked by another process, and local Chromium could not
  be executed from this shell (`Permission denied`), so rendered measurement ran through Claude
  in Chrome at desktop width only. **The per-breakpoint figures above come from the served CSS
  media queries**, which carry the complete type scale; the 1200/810 columns are declared values,
  not measured ones.
- The built-in browser pane was re-tested and still reports `innerWidth: 0` — unusable, as
  recorded.
- `--framer-font-family` appears HTML-entity-encoded in inline styles; a scan that does not
  decode `&quot;` reports a phantom `&quot` family and undercounts every real one.
- Style presets map `data-styles-preset="<id>"` in the markup to a
  `.framer-styles-preset-<hash>` CSS class; the hash is what carries the type properties and the
  id is what the canvas names. Both are needed to go from a rendered element to a named style.
- **`framer.getFont("Geist Mono")` resolves**, returning a live `Font`
  (`GF;Geist Mono-regular`, w400) that can be assigned straight to a node's `font` in the same
  `exec`. The recorded rule that font lookups return `null` applies to **custom uploads** such as
  Gellix; fonts from Framer's built-in Google catalogue look up fine, so no donor node is needed
  for those. Note the lookup takes the **family name**, not the selector — `"GF;Geist Mono-regular"`
  returns `null`.
- **The publish preview lagged the write by about 25 seconds, on a FRESH session.** The first read
  returned 9 changes with mine absent; a second fresh read 25s later returned 10 including
  `SmartComponent | Footer / Footer`. The recorded guidance is to use a fresh session because a
  stale one reports `changesCount: 0` — that is necessary but not sufficient. **Read the preview
  twice with time between, and require your own change to appear before trusting the rest of the
  list.**

### !!! THE PREDICTED COUNT WAS WRONG: 18 -> 24, NOT 18 -> 21 !!!

The pre-publish baseline below predicted `"Geist Mono"` would go **18 -> 21**. It went **18 -> 24**
on every one of the seven pages checked. The site is right and the prediction was wrong:

```
pre    6 x  font-family: 'Geist Mono'        6 x  Geist Mono&quot    6 x  Geist Mono Placeholder&quot   = 18

the unchanged `@font-face` declarations. **When predicting a grep count, count what the grep matches,
not what you changed.**

## Method notes

- **`framer.getFont(family, { weight })` works** and returns distinct faces —
  `GF;Inter-regular`, `GF;Inter-500`, `GF;Inter-600`, `GF;Inter-700`. The recorded note only
  established the single-argument form.
- **`getNodesWithAttributeSet("font")` returns 0** — `font` is not indexed by that method, so a
  tree walk is the only way to enumerate node fonts. (`zIndex` is indexed but returns `undefined`
  values; `font` returns nothing at all.)
- **Writes cascade across breakpoints.** A scan found 24 target nodes on `/elements` + `/contact`
  and the write touched **7**; the breakpoint copies picked it up. Confirmed rather than assumed —
  a re-scan returned `HITS 0`.
- **`run_in_background` plus `&` inside the command detaches the real work**, which is then killed
  when the wrapper exits. The first project walk produced a 0-byte file this way. Run the command
  directly and let the harness background it — and note `tee` buffers, so nothing lands until it
  finishes.

## The forcing function, found — a PERSISTENT trivial change re-dirties the component

Done 2026-10-25. Both stale components are now queued to re-emit, and no font was touched.

**Selection can be made verifiable by renaming the target first.** Automation cannot read the
Framer layer tree's selection — there is no marker, the whole tree uses two class names, and
`framer.getSelection` genuinely **does not exist** in this scope (`typeof` is `undefined`;
re-probed rather than taken on trust). The way through is to **rename the target node through the
API to something unique**, filter the layer tree by that name, and the match is then unambiguous —
confirmed here by a zoomed capture showing the purple highlight on the renamed row. The same trick
is recorded for disambiguating a duplicate variant; it works just as well for confirming a click.

**A rename does not always cascade, and whether it does is the useful signal.** `ZZTARGET-BUTTON`
landed on **exactly one** node (`IsPmXClw2aNAbgzPM4`), while `ZZTARGET-TITLE` cascaded to **all
six** variants of `News / News Article`. So a non-cascading rename gives a unique handle; a
cascading one tells you the layer is shared.

**!!! A CHANGE-AND-REVERT IS NET ZERO AND FRAMER DROPS IT FROM PENDING. !!!** After renaming both
targets and renaming them back, `News / News Article` **disappeared from the publish preview** —
Framer diffed it to clean, so it would not have rebuilt and the stale CSS would have survived.

## !!! CORRECTION — IT IS NOT STALE CSS. THE REBUILD THEORY IS WRONG AND IS WITHDRAWN !!!

Published 2026-10-25 19:20 UTC. **Both components rebuilt and the General Sans did not move.**

The two sections above diagnosed this as stale output from components that had not been rebuilt,
and prescribed forcing them dirty. That diagnosis is **false**, and the publish disproved it:

- The rename **shipped** — `data-framer-name="Article Title"` appears 8 times on `/news`, so
  `News / News Article` demonstrably rebuilt.
- The counts did not move: Home still renders **10** General Sans references, each news page **2**.
- The component scope hashes `framer-7EyT7` and `framer-93Sqd` are **unchanged**, so those hashes
  are not build hashes at all — they are stable per-component identifiers.

**The decisive measurement, in a page built minutes earlier:**

```
.framer-9oRcZ .framer-styles-preset-1a0fnmv  ->  Inter
.framer-93Sqd .framer-styles-preset-1a0fnmv  ->  General Sans
```

Same preset, same style, same build, two variant scopes of the **same component**, two different
families.

**And the document is byte-identical across those variants.** All **14** button labels read
`style = KO4lJWHBT (Button Primary / Inter 500)` with `font = UNSET`. There is no difference in
the document to explain the difference in the output.

**So the General Sans is stored somewhere the node API cannot see or reach** — a per-variant
resolved-style value frozen when the variant was created, most likely, since `Button White to
Black` was adopted by the Methodology button well before `Button Primary` became Inter. It is
real data, not a cache, and no amount of rebuilding clears it.

**What is NOT worth repeating**: forcing the component dirty. That was tried, it worked as a
dirty-flag mechanism (both components were pending on two agreeing fresh reads and both rebuilt),
and it changed nothing. Two publishes were spent on it.

**What might still work, untested**: in the editor, on the `Button White to Black` variant's label,
press **Remove** on the style pill and re-apply `Button Primary`. Removing detaches and bakes
literals, which would overwrite whatever frozen value is held. Re-applying may restore the frozen
value or may re-resolve it — unknown. Leaving it detached would certainly fix the render, at the
cost of that one label no longer following the style.

**All three Methodology buttons are instances of a REMOTE module copy of `Utilities / Primary

The variant names were a red herring throughout. The distinction was local vs remote the whole
time, and this file already recorded that the Methodology buttons sit on a third module — the note
was read, cited in this very session, and then not acted on.

**The lesson, which this project has now learned four times** (`Valide/Scroll_Progress`, the
`/products` + `/elements` footer, the 57 download buttons, and now this): **when an edit to a
component provably lands in the document and provably does not appear on the page, check
`componentIdentifier` before any other theory.** A `module:` prefix means a remote copy and your
edit can never reach it. It is one `exec` and it would have saved four publishes here.
